# MomentBid — Requirements Specification Document

**Project Name:** MomentBid  
**Version:** 1.4  
**Date:** March 23, 2026  
**Team Size:** 3 Members  
**Blockchain:** WireFluid Network  
**Hackathon Context:** PSL Use Case — Triple Points Category

---

## 1. Executive Summary

MomentBid is a pre-commitment conditional auction protocol for broadcast ad inventory, built on the WireFluid blockchain. It enables brands to commit sealed bids before a PSL match for specific cricket event types (over breaks, wicket falls, last-over thrillers, etc.). When events occur during live play, the smart contract autonomously resolves the auction, selects the highest eligible bidder while enforcing competitor separation rules, instructs the broadcaster which ad to play, and settles all payments atomically. If an event never triggers, brands receive a partial refund with a small reservation fee going to the broadcaster.

## 2. Stakeholders and Roles

### 2.1 Platform Admin (Your Team)

The entity that deploys and operates the protocol infrastructure.

**Responsibilities:**
- Deploy and manage smart contracts on WireFluid
- Onboard broadcasters by granting them the BROADCASTER_ROLE
- Onboard brands by registering their wallets
- Set the platform fee percentage (taken only on successful auction settlements)
- Assign ORACLE_ROLE to the match simulator wallet (hackathon) or backend server wallet (production)
- Monitor all system activity, transaction volumes, and fee revenue
- Execute emergency pause/unpause of the entire protocol
- Override exclusion group configuration for dispute resolution only (when broadcaster and affected brands mutually agree a correction is needed before bidding opens)
**Access Level:** Highest. Can configure all system parameters. Cannot manipulate auction outcomes or access escrowed brand funds.

### 2.1.2 Oracle (Match Simulator / Production Backend)

**Responsibilities:**
- Make triggers for each event.
- The admin clicks on that event to trigger it manually

**Access Level:** Can only call event trigger and match lifecycle functions. Cannot access funds, modify bids, or change auction parameters.


### 2.2 Broadcaster (PTV Sports, Daraz, etc.)

The entity that owns ad inventory and delivers ads to viewers through television broadcast.

**Responsibilities:**
- Create matches in the system (date, teams, venue)
- Define which event types are auctionable for each match
- Set reserve prices per event type per match
- Create and configure exclusion groups (define brand groupings, separation distances, cross-event flags)
- Set reservation fee percentage per event type (1-5%)
- Transition match from CREATED to OPEN (locks all match parameters and exclusion group configurations, opens bidding to brands)
- Receive auction winner instructions (which brand's ad to play)
- Mark matches as started and completed
- View earnings dashboard

**Access Level:** Can manage their own matches, inventory, and exclusion groups. Cannot modify exclusion groups or match parameters after match transitions to OPEN.Can view bid amount. Cannot override auction outcomes.

### 2.3 Brands (Pepsi, KFC, Jazz, HBL, etc.)

The entities that bid for ad slots during PSL matches.

**Responsibilities:**
- Deposit tokens into the bidding vault before for bidding
- Configure conditional bids per event type with maximum amounts
- Set a total match budget cap
- Pre-upload ad creative references (IPFS hash or CDN URL) per event type
- View auction results, spending history, and refund status after matches

**Access Level:** Can only manage their own bids and view their own transaction history. Can see other brands' bid amounts. Cannot withdraw escrowed funds until match is completed and refunds are processed.

## 3. Functional Requirements

### 3.1 Match Management

**FR-3.1.1:** The broadcaster SHALL be able to create a new match by providing: match date, team A name, team B name, and venue name.

**FR-3.1.2:** Each match SHALL have a unique match ID generated by the smart contract.

**FR-3.1.3:** The broadcaster SHALL be able to define which event types are enabled for auction for each match from the following list:

- OVER_BREAK (occurs at the end of every over)
- STRATEGIC_TIMEOUT (occurs at scheduled timeout breaks)
- INNINGS_BREAK (occurs between first and second innings)
- WICKET_FALL (occurs when any wicket falls)
- HIGH_VALUE_WICKET (occurs when a batsman with 30+ runs is dismissed)
- LAST_OVER_THRILLER (occurs when required run rate exceeds 10 in the final over)
- HAT_TRICK_BALL (occurs when a bowler has taken 2 wickets in 2 consecutive deliveries)
- SUPER_OVER (occurs when match scores are tied at end of regulation)

**FR-3.1.4:** The broadcaster SHALL be able to set a reserve price (minimum acceptable bid) for each enabled event type. If no bid meets the reserve, the slot goes to a default house ad and no auction settles.

**FR-3.1.5:** The broadcaster SHALL be able to set a reservation fee percentage (1-5%) for each enabled event type. This fee is deducted from brand refunds when the event never triggers.

**FR-3.1.5a:** The broadcaster SHALL be able to set a slot count per event type, representing how many ads are shown during that event's ad break. Default slot counts:
- OVER_BREAK: 3 slots
- STRATEGIC_TIMEOUT: 5 slots
- WICKET_FALL: 2 slots
- HIGH_VALUE_WICKET: 2 slots
- LAST_OVER_THRILLER: 1 slots
- HAT_TRICK_BALL: 1 slots
- SUPER_OVER: 1 slots
- INNINGS_BREAK: 12 slots

The broadcaster MAY adjust these values per match based on their actual ad break durations.

**FR-3.1.6:** A match SHALL have the following lifecycle states:
- CREATED → match is set up, broadcaster configures event types, reserve prices, reservation fees, and exclusion groups. No bids accepted. Broadcaster can freely edit all parameters.
- OPEN → broadcaster has finalized configuration and explicitly opened bidding. All match parameters and exclusion group configurations are now locked and cannot be modified. Brands can commit and reveal bids during this phase.
- ACTIVE → match has started, no new bids accepted, oracle can trigger events and auctions resolve.
- COMPLETED → match has ended, refunds are processed for unsettled bids.
- CANCELLED → match is cancelled at any point. Already-settled auctions are final (no refund). All unsettled bids are refunded in full with zero reservation fee.

**FR-3.1.7:** Only the broadcaster or platform admin SHALL be able to transition match states.

### 3.2 Exclusion Group Management

**FR-3.2.1:** The broadcaster SHALL be able to create exclusion groups containing multiple brand wallet addresses (e.g., Group 1: Pepsi, Coca-Cola, 7Up, Fanta).

**FR-3.2.2:** Each exclusion group SHALL have a configurable minimum separation distance (number of slots between competitors). Default is 1 (no adjacent slots).

**FR-3.2.3:** Each exclusion group SHALL have a configurable crossEventSeparation boolean flag. When true, winning ANY event type counts toward the separation counter. When false, only the same event type is tracked.

**FR-3.2.4:** Exclusion group configuration (adding/removing brands, changing separation distance, changing cross-event flag) SHALL only be permitted while all matches using those groups are in CREATED state. Once any match transitions to OPEN, the exclusion group configuration SHALL be locked and cannot be modified by the broadcaster. This ensures brands bid with full knowledge of the rules, and those rules cannot change after bids are committed.

**FR-3.2.5:** The platform admin SHALL retain an override capability to modify exclusion groups for dispute resolution purposes only, even after a match has moved to OPEN. This is an emergency measure, not a routine operation.

**FR-3.2.6:** Exclusion group rules SHALL be enforced automatically during every auction resolution. If the highest bidder is in the same exclusion group as a recent winner (within the separation distance), their bid SHALL be skipped and the next highest eligible bidder SHALL be selected.

**FR-3.2.7:** If no eligible bidder exists after exclusion group filtering, the contract SHALL emit a NoEligibleBidder event and no auction SHALL settle for that slot.

### 3.3 Brand Bidding

**FR-3.3.1:** A brand SHALL be able to place bids for a specific match by specifying: event type, bid amount, and creative reference (IPFS hash or URL).

**FR-3.3.2:** A brand SHALL be able to set a total budget cap per match. The sum of all actual settlements SHALL NOT exceed this cap.

**FR-3.3.3:** When a brand places a bid, the bid amount SHALL be immediately escrowed in the smart contract. The brand cannot withdraw escrowed funds until the match is COMPLETED or CANCELLED.

**FR-3.3.4:** Bids SHALL be open and visible on-chain. All brands can see all other brands' bid amounts and event type selections. This transparency creates competitive pressure that drives prices up, benefiting the broadcaster.

**FR-3.3.5:** A brand SHALL be able to increase their bid for an event type while the match is in OPEN state. The additional tokens are escrowed immediately. A brand SHALL NOT be able to decrease their bid or withdraw a placed bid — this prevents gaming where a brand places a high bid to scare off competitors then lowers it at the last moment.

**FR-3.3.6:** A brand SHALL be able to place bids for multiple event types in a single match.

**FR-3.3.7:** Bids SHALL only be accepted while the match state is OPEN. Bids SHALL NOT be accepted during CREATED (match still being configured), ACTIVE (match in progress), COMPLETED, or CANCELLED states.

**FR-3.3.8:** If a brand's remaining escrowed budget (after previous settlements) falls below their bid for an event type, they SHALL be automatically excluded from that event type's auction.

### 3.4 Auction Resolution

**FR-3.4.1:** When the oracle triggers an event, the smart contract SHALL resolve the auction for that event type by selecting the top N eligible bidders, where N is the slot count configured by the broadcaster for that event type. The resolution SHALL use a **max-iteration approach** (NOT on-chain sorting) for gas efficiency. For each slot position (1 through N):
1. Iterate through ALL bids for the triggered event type
2. For each bid, check eligibility: (a) not already settled/won a slot in this trigger, (b) does not violate exclusion group rules against winners from recent previous event triggers AND against winners already selected in this trigger, (c) remaining budget is sufficient, (d) bid meets or exceeds reserve price
3. Track the highest eligible bid amount and its brand during the iteration
4. At the end of the iteration, the tracked highest eligible bidder wins this slot position
5. Mark the winner as settled so they are skipped in subsequent slot iterations
6. Repeat for the next slot position until all N slots are filled or no eligible bidder is found

This approach is O(N × S) where N = number of bidders and S = number of slots. For the worst case of 20 bidders and 8 slots (SUPER_OVER), this is 160 simple comparison iterations with no memory allocation for sorting.

**FR-3.4.2:** Auction settlement SHALL be atomic. In a single transaction, the contract SHALL settle ALL slots for the triggered event. To minimize gas cost, token transfers SHALL be batched:
- For each winning slot: deduct the winning bid amount from the winner's escrow, calculate broadcaster share and platform fee, accumulate totals, record the winner in recent winners history, emit an AuctionSettled event containing: matchId, eventType, winner address, amount, creative reference, slotPosition
- After ALL slots are resolved: execute exactly TWO token transfers — one aggregated transfer to the broadcaster wallet and one aggregated transfer to the platform wallet. This reduces token transfers from 2×N (where N = slots filled) to exactly 2, saving approximately 9,000 gas per eliminated transfer.

**FR-3.4.3:** The platform fee SHALL be a configurable percentage set by the platform admin. Default: 5%.

**FR-3.4.4:** If no eligible bid exists for ANY slot (all bids filtered out or no bids committed for that event type), the contract SHALL emit a NoEligibleBidder event for that slot and no funds SHALL move for that slot.

**FR-3.4.5:** If the number of eligible bidders is less than the slot count, the contract SHALL fill as many slots as possible and emit a PartialFill event indicating: matchId, eventType, slotsFilled, totalSlots. The unfilled slots are left for the broadcaster to fill with their own house ads or pre-sold inventory.

**FR-3.4.6:** Slot positions SHALL be assigned in descending order of bid amount. Slot 1 (most premium position, played first in the ad break) goes to the highest bidder. Slot 2 goes to the second highest, and so on. The broadcaster receives the full ordered playlist of winning brands and their slot positions.

### 3.5 Refund Processing

**FR-3.5.1:** When a match transitions to COMPLETED, the contract SHALL process refunds for all unspent escrowed funds.

**FR-3.5.2:** For event types that triggered and the brand LOST the auction: (100% minus reservation fee percentage) of the escrowed bid amount SHALL be refunded to the brand.

**FR-3.5.3:** For event types that NEVER triggered during the match: the brand SHALL receive (100% minus reservation fee percentage) of their escrowed bid. The reservation fee SHALL be transferred to the broadcaster's wallet. The platform takes no cut of the reservation fee.

**FR-3.5.4:** When a match is CANCELLED, the following refund rules SHALL apply:
- For bids that have already been settled (event triggered, brand won, ad was displayed): NO refund. The settlement is final. The broadcaster delivered real value and retains their share. The platform retains its fee.
- For bids where the event triggered but the brand lost the auction: already refunded at (100% minus reservation fee percentage) during normal auction resolution. No additional action needed.
- For bids where the event has NOT yet triggered at the time of cancellation: 100% refund to the brand. Zero reservation fee. The brand SHALL NOT be penalized for events that were prevented by circumstances outside anyone's control (rain, technical failure, etc.).

**FR-3.5.5:** Brands SHALL be able to call a claimRefund() function after a match is COMPLETED. Alternatively, the platform admin SHALL be able to trigger batch refunds for all brands in a single transaction.

### 3.6 Oracle System

**FR-3.6.1:** Only wallets with the ORACLE_ROLE SHALL be able to call the triggerEvent() function.

**FR-3.6.2:** The oracle SHALL provide the following parameters when triggering an event: matchId and eventType.

**FR-3.6.3:** The oracle SHALL NOT be able to trigger events for matches that are not in ACTIVE state.

**FR-3.6.4:** The oracle SHALL NOT be able to trigger the same event type more than the maximum allowed times per match (configurable per event type by the broadcaster). Example: STRATEGIC_TIMEOUT max 4 per match, SUPER_OVER max 1 per match. OVER_BREAK max 40 per match. WICKET_FALL max 20 per match.

**FR-3.6.5:** For the hackathon MVP, the oracle SHALL be a match simulator dashboard operated manually by a team member. The simulator SHALL:
- display some events like superover,wicket,overbreak etc. By clickng on that the event will be trigger.
- Instead of automatically identify the event thru match feed we will be generating event manually by clickng on the button on UI

## 4. Non-Functional Requirements

### 4.1 Security

**NFR-4.1.1:** All contracts SHALL inherit from OpenZeppelin ReentrancyGuard on every external function that moves tokens.

**NFR-4.1.2:** All contracts SHALL use OpenZeppelin AccessControl with the following roles: DEFAULT_ADMIN_ROLE, BROADCASTER_ROLE, ORACLE_ROLE, BRAND_ROLE.

**NFR-4.1.3:** All contracts SHALL inherit from OpenZeppelin Pausable. The platform admin SHALL be able to pause all operations in case of emergency.

**NFR-4.1.4:** Token approvals SHALL request only the exact amount needed for each transaction. The frontend SHALL NEVER request unlimited (type(uint256).max) approvals.

**NFR-4.1.5:** Bids are intentionally open and visible on-chain. Front-running protection (commit-reveal) is not required because the bidding window spans hours or days before a match, not milliseconds. Visible bids create competitive pressure that benefits the broadcaster through price discovery. Brands can increase bids in response to competitors but cannot decrease or withdraw bids, preventing last-moment manipulation.

**NFR-4.1.6:** Custom errors SHALL be used instead of require strings for gas efficiency: e.g., error InsufficientBid(uint256 required, uint256 provided).

**NFR-4.1.7:** All escrowed funds SHALL only be accessible through auction settlement or refund functions. No admin, broadcaster, or oracle role SHALL have a function to directly withdraw escrowed brand funds.

### 4.2 Gas Optimization

**NFR-4.2.1:** All auction resolution SHALL execute in a single transaction regardless of the number of bidders.

**NFR-4.2.2:** Auction resolution SHALL NOT use on-chain sorting algorithms. Instead, a max-iteration approach SHALL be used: for each slot, iterate through all bids tracking the highest eligible bid. This avoids memory allocation for sorted arrays and reduces gas to simple comparison operations. Worst case (20 bidders, 8 slots) = 160 iterations of reads and comparisons.

**NFR-4.2.3:** Token transfers SHALL be batched within auction resolution. Instead of transferring to the broadcaster and platform separately for each slot (2 × N transfers), the contract SHALL accumulate totals across all slots and execute exactly 2 transfers at the end of resolution — one to the broadcaster, one to the platform. This saves approximately 9,000 gas per eliminated transfer (up to 126,000 gas saved for an 8-slot SUPER_OVER).

**NFR-4.2.4:** On-chain storage SHALL be minimized. Ad creative content, match metadata, and venue information SHALL be stored off-chain (IPFS or CDN) with only content hashes stored in the contract.

**NFR-4.2.5:** Events SHALL be used for historical data instead of on-chain storage. The frontend SHALL reconstruct historical state from event logs rather than storing full history in contract mappings.

**NFR-4.2.6:** Batch operations SHALL be supported where possible. Batch refund processing SHALL allow processing multiple brands in a single transaction.

**NFR-4.2.7:** The maximum number of bidders per event type per match SHALL be capped at 20 to bound the worst-case gas cost of auction resolution.

**NFR-4.2.8: Gas Budget Analysis (WireFluid-specific)**

WireFluid uses the WIRE token for gas with a minimum gas price of 10 Gwei and ~5 second block finality. The following gas estimates are based on standard EVM operation costs:

Worst-case scenario — SUPER_OVER with 8 slots and 20 bidders:

| Operation | Gas Cost |
|---|---|
| Base transaction cost | 21,000 |
| Read 20 bids (20 × 200 SLOAD) | 4,000 |
| Max-iteration: 160 comparisons (20 bidders × 8 slots × ~200 gas) | 32,000 |
| Exclusion group checks (~160 SLOADs) | 32,000 |
| Budget checks (~20 SLOADs) | 4,000 |
| 8 escrow balance updates (8 × 20,000 SSTORE) | 160,000 |
| 2 batched token transfers (2 × ~9,000) | 18,000 |
| 8 event emissions (8 × ~1,500) | 12,000 |
| **Total estimated** | **~283,000** |

At WireFluid's minimum gas price of 10 Gwei: 283,000 × 10 Gwei = 0.00283 WIRE. This is cheaper than a standard ERC-20 contract deployment on WireFluid (~0.012 WIRE) and well within any reasonable block gas limit.

Typical case — OVER_BREAK with 3 slots and 15 bidders: estimated ~120,000 gas = 0.0012 WIRE. Negligible.

### 4.3 Reusability

**NFR-4.3.1:** Smart contracts SHALL be modular and use interfaces. The following interfaces SHALL be defined:
- IOracle — any oracle data source can implement this
- IAuctionEngine — the core auction resolution logic, reusable for any event-driven auction
- IInventoryManager — match and inventory management, reusable for any live event
- IExclusionManager — competitor separation logic, reusable for any multi-party marketplace

**NFR-4.3.2:** The auction engine SHALL NOT contain cricket-specific logic. Event types SHALL be generic uint8 enums configurable at deployment. A new deployer could use the same contracts for IPL, Premier League football, concerts, or any live event.

**NFR-4.3.3:** All contracts SHALL use the ERC-2981 royalty standard for any future secondary marketplace extensions.

**NFR-4.3.4:** All contracts SHALL use OpenZeppelin's upgradeable proxy pattern or SHALL be designed with clearly documented upgrade paths.

### 4.4 OpenZeppelin Standards Compliance

**NFR-4.4.1:** The following OpenZeppelin contracts SHALL be used:
- ERC721 or ERC1155 for ad inventory tokens
- ERC2981 for on-chain royalty standard
- AccessControl for role-based permissions
- ReentrancyGuard for protection against reentrancy attacks
- Pausable for emergency stop functionality
- ERC20 interface for the bidding token (or native token wrapping)

**NFR-4.4.2:** All contracts SHALL follow Solidity style guide conventions and include NatSpec documentation on every public and external function.

### 4.5 RPC Efficiency

**NFR-4.5.1:** The frontend SHALL use WebSocket event subscriptions (eth_subscribe) instead of polling for real-time updates.

**NFR-4.5.2:** The frontend SHALL use multicall patterns to batch multiple read calls into a single RPC request.

**NFR-4.5.3:** The frontend SHALL cache static data (exclusion groups, match metadata, event type configurations) locally after first fetch and only refresh on relevant contract events.

**NFR-4.5.4:** The frontend SHALL display clear transaction lifecycle states: Pending → Confirmed → Finalized. No action SHALL be shown as confirmed before sufficient block confirmations.

**NFR-4.5.5:** The frontend SHALL implement automatic retry with gas price bumping for dropped transactions.

### 4.6 UI/UX

**NFR-4.6.1:** Wallet connection SHALL automatically detect if the user is on the wrong network and prompt them to switch to WireFluid.

**NFR-4.6.2:** Every transaction SHALL display a human-readable description in MetaMask's confirmation popup through proper function naming and NatSpec comments.

**NFR-4.6.3:** All monetary values SHALL be displayed in a human-readable format (not raw wei/token decimals).

**NFR-4.6.4:** Error states SHALL be handled gracefully with clear user-facing messages, not raw blockchain error codes.

## 5. Smart Contract Architecture

### 5.1 Contract: MomentBidCore.sol

**Purpose:** The main auction engine. Handles bid commitments, auction resolution, payment settlement, and refund processing.

**Inherits:** AccessControl, ReentrancyGuard, Pausable

**Key State Variables:**
- mapping(uint256 => Match) public matches — match ID to match data
- mapping(uint256 => mapping(uint8 => Bid[])) internal commitedBids — matchId → eventType → array of bids
- mapping(uint256 => address[]) public recentWinners — matchId → ordered list of recent auction winners
- mapping(uint256 => mapping(address => uint256)) public escrowBalance — matchId → brand → escrowed amount
- mapping(uint256 => mapping(address => uint256)) public budgetCap — matchId → brand → max total spend
- mapping(uint256 => mapping(address => uint256)) public totalSpent — matchId → brand → actual spend so far
- uint256 public platformFeePercent — platform fee (default 5%)

**Key Structs:**
```
struct Match {
    address broadcaster;
    uint8 state;            // 0=CREATED, 1=OPEN, 2=ACTIVE, 3=COMPLETED, 4=CANCELLED
    uint8[] enabledEvents;
    mapping(uint8 => uint256) reservePrice;
    mapping(uint8 => uint256) reservationFeePercent;
    mapping(uint8 => uint8) maxTriggers;
    mapping(uint8 => uint8) triggerCount;
    mapping(uint8 => uint8) slotCount;  // number of ad slots per event type
}

struct Bid {
    address brand;
    uint256 amount;
    bool settled;
    string creativeRef;     // IPFS hash or CDN URL
}
```

**Key Functions:**
- placeBid(uint256 matchId, uint8 eventType, string creativeRef) external payable
- increaseBid(uint256 matchId, uint8 eventType) external payable
- setBudgetCap(uint256 matchId, uint256 cap) external
- triggerEvent(uint256 matchId, uint8 eventType) external onlyRole(ORACLE_ROLE)
- claimRefund(uint256 matchId) external
- batchRefund(uint256 matchId, address[] brands) external onlyRole(DEFAULT_ADMIN_ROLE)

**Key Events:**
```
event MatchCreated(uint256 indexed matchId, address indexed broadcaster);
event BidPlaced(uint256 indexed matchId, uint8 indexed eventType, address indexed brand, uint256 amount);
event BidIncreased(uint256 indexed matchId, uint8 indexed eventType, address indexed brand, uint256 newAmount);
event AuctionSettled(uint256 indexed matchId, uint8 eventType, address winner, uint256 amount, string creativeRef, uint8 slotPosition);
event PartialFill(uint256 indexed matchId, uint8 eventType, uint8 slotsFilled, uint8 totalSlots);
event NoEligibleBidder(uint256 indexed matchId, uint8 eventType, uint8 slotPosition);
event RefundProcessed(uint256 indexed matchId, address indexed brand, uint256 refundAmount, uint256 reservationFee);
event MatchStateChanged(uint256 indexed matchId, uint8 newState);
```

### 5.2 Contract: ExclusionManager.sol

**Purpose:** Manages exclusion groups and enforces competitor separation rules. Owned by the broadcaster with a locking mechanism tied to match state.

**Inherits:** AccessControl

**Key State Variables:**
- mapping(address => uint256) public brandExclusionGroup — brand wallet → group ID
- mapping(uint256 => uint256) public separationDistance — group ID → minimum slot gap
- mapping(uint256 => bool) public crossEventSeparation — group ID → applies across event types
- mapping(uint256 => bool) public groupLocked — group ID → whether the group is locked (any match using it has moved to OPEN)

**Key Functions:**
- createExclusionGroup(uint256 groupId, address[] brands, uint256 separation, bool crossEvent) external onlyRole(BROADCASTER_ROLE)
- addBrandToGroup(uint256 groupId, address brand) external onlyRole(BROADCASTER_ROLE) onlyWhenUnlocked(groupId)
- removeBrandFromGroup(address brand) external onlyRole(BROADCASTER_ROLE) onlyWhenUnlocked(groupId)
- updateSeparation(uint256 groupId, uint256 newSeparation) external onlyRole(BROADCASTER_ROLE) onlyWhenUnlocked(groupId)
- lockGroup(uint256 groupId) external — called automatically when any match using this group transitions to OPEN
- adminOverride(uint256 groupId, address[] brands, uint256 separation, bool crossEvent) external onlyRole(DEFAULT_ADMIN_ROLE) — emergency override for dispute resolution only
- isEligible(address brand, address[] recentWinners) external view returns (bool)

### 5.3 Contract: OracleController.sol

**Purpose:** Manages oracle permissions and validates event triggers.

**Inherits:** AccessControl

**Key Functions:**
- triggerEvent(uint256 matchId, uint8 eventType) external onlyRole(ORACLE_ROLE)
- Validates match is in ACTIVE state
- Validates event type is enabled for this match
- Validates trigger count has not exceeded maximum for this event type
- Calls MomentBidCore.resolveAuction()

### 5.4 Contract: AdInventoryNFT.sol (Optional Enhancement)

**Purpose:** Represents ad slots as ERC721 tokens with ERC2981 royalty standard for future extensibility.

**Inherits:** ERC721, ERC2981, AccessControl

**Note:** For the hackathon MVP, this contract may be simplified or deferred. The core auction functionality in MomentBidCore.sol does not depend on NFT tokenization. This contract exists for future secondary marketplace extensions and to demonstrate OpenZeppelin standards compliance to judges.

## 6. Frontend Architecture

### 6.1 Brand Dashboard

**Pages:**

**6.1.1 Match Browser**
- List of upcoming matches with date, teams, venue
- Match status indicator (CREATED / OPEN / ACTIVE / COMPLETED)
- Click into any OPEN match to view available event types, slot counts, and place bids

**6.1.2 Bid Configuration (per match)**
- List of enabled event types with their reserve prices and slot counts (e.g., "OVER_BREAK — Reserve: 100K — 3 slots per break")
- For each event type: input field for bid amount, upload field for creative reference
- Current bid leaderboard per event type — shows all brands' bid amounts ranked (brands can see competitors' bids and decide whether to increase their own)
- "Increase Bid" button per event type (only increases allowed, no decreases)
- Note: a brand bids once per event type. Their single bid competes for one of the N available slots. They cannot win more than one slot per event trigger.
- Total match budget cap input
- Submit bid button (single transaction per bid, tokens escrowed immediately)
- Display total escrowed amount and remaining budget

**6.1.3 Live Match View**
- Real-time event feed showing triggered events
- Auction results as they settle — showing the full ad playlist per event (Slot 1: KFC, Slot 2: Jazz, Slot 3: HBL)
- Brand's own bid status per event type (pending / won with slot position / lost / not triggered)
- Running total of money spent this match
- Remaining escrowed balance

**6.1.4 History and Refunds**
- List of past matches with total spent and total refunded
- Per-match breakdown: which events triggered, which bids won, which were refunded
- Reservation fees deducted per match
- Claim refund button for completed matches

### 6.2 Broadcaster Admin Panel

**Pages:**

**6.2.1 Match Management**
- Create new match form (date, teams, venue)
- List of all matches with state indicators
- Edit match (add/remove event types, adjust reserve prices, adjust reservation fees)
- Match lifecycle buttons: Start Match → Complete Match / Cancel Match

**6.2.2 Exclusion Group Configuration**
- List of all exclusion groups with member brands
- Create new group: add brands, set separation distance, set cross-event flag
- Edit existing groups

**6.2.3 Live Match Monitor**
- Real-time feed of auction settlements during an active match
- Per-event ad playlist: ordered list of winning brands with slot positions, amounts, and creative references — this IS the instruction to the broadcast control room
- PartialFill alerts when fewer brands won than available slots (broadcaster fills remaining with house ads)
- NoEligibleBidder alerts
- Running total of revenue earned this match

**6.2.4 Earnings Dashboard**
- Total revenue across all matches (auction settlements + reservation fees)
- Per-match revenue breakdown
- Per-event-type revenue analytics (which event types generate the most revenue)
- Exportable transaction history

### 6.3 Platform Admin Panel

**Pages:**

**6.3.1 System Overview**
- Total matches created, active, completed
- Total transaction volume (all time, this season)
- Total platform fees earned
- Total brands and broadcasters registered

**6.3.2 User Management**
- Register new broadcaster (assign BROADCASTER_ROLE)
- Register new brand (assign BRAND_ROLE, assign to exclusion group)
- Register oracle wallet (assign ORACLE_ROLE)
- View all registered users and their roles

**6.3.3 Protocol Configuration**
- Set/adjust platform fee percentage
- View all deployed contract addresses
- Emergency pause/unpause toggle
- Contract verification status on WireFluid block explorer

**6.3.4 Transaction Monitor**

## 8. Payment Flow Summary

### 8.1 Before Match (Bidding Phase)
```
Brand deposits tokens → Tokens escrowed in MomentBidCore contract
                        (Brand cannot withdraw until match COMPLETED/CANCELLED)
```

### 8.2 During Match (Auction Settlement)
```
Oracle triggers event → Contract resolves auction for N slots (N = slotCount for this event type)
                      → For each slot (1 through N), the highest eligible bidder wins:
                            Slot 1 (premium position): highest bidder
                            Slot 2: second highest bidder
                            ...
                            Slot N: Nth highest bidder
                      → Each winner's escrowed tokens are distributed:
                            95% → Broadcaster wallet
                             5% → Platform wallet
                      → If fewer than N eligible bidders, remaining slots are unfilled (broadcaster uses house ads)
                      → Losing bidders (ranked below slot N) tokens remain escrowed for future events
```

### 8.3 After Match (Refund Processing)
```
Match marked COMPLETED → For each brand's remaining escrowed funds:

  If bid was for an event that triggered but brand LOST:
      → 100% refunded to brand

  If bid was for an event that NEVER triggered:
      → (100% - reservationFee%) refunded to brand
      → reservationFee% sent to broadcaster
      → Platform gets nothing from reservation fees

Match marked CANCELLED → Different rules apply:

  If bid was already settled (event triggered, brand won, ad displayed):
      → No refund. Settlement is final. Broadcaster and platform keep their shares.

  If bid was for an event that triggered but brand LOST:
      → Already refunded at 100% during normal resolution. No action needed.

  If bid was for an event that has NOT yet triggered:
      → 100% refunded to brand (zero reservation fee)
```

## 11. Glossary

| Term | Definition |
|---|---|
| Open Bidding | Bids are placed openly and are visible on-chain to all participants. Brands can see competitors' bids and increase their own (but not decrease). This creates competitive pressure that drives prices up, benefiting the broadcaster. Front-running protection is unnecessary because the bidding window spans hours/days, not milliseconds. |
| Exclusion Group | A set of competing brands that cannot appear in the same ad break or in adjacent ad breaks. Enforced by the smart contract both within a single event trigger (intra-event) and across consecutive triggers (cross-event). |
| Separation Distance | The minimum number of auction settlements between brands in the same exclusion group across consecutive event triggers. |
| Slot Count | The number of ad slots available within a single event trigger's ad break. For example, an OVER_BREAK with slotCount=3 means three brands win three positions in that ad break. Configured by the broadcaster per event type per match. |
| Slot Position | The rank of a winning brand within a multi-slot ad break. Position 1 (highest bidder) is the most premium slot played first. |
| Reserve Price | The minimum acceptable bid for an event type. Bids below this are ignored. |
| Reservation Fee | A small percentage (1-5%) deducted from brand refunds when an event never triggers. Compensates the broadcaster for reserving inventory. Goes 100% to the broadcaster. |
| Partial Fill | When an event trigger has N slots but fewer than N eligible bidders. The contract fills as many slots as possible and the broadcaster fills the rest with house ads. |
| Oracle | The entity that reports live cricket events to the smart contract. A match simulator for the hackathon. A backend server connected to a data feed for production. |
| Escrow | Tokens locked in the smart contract after a brand commits a bid. Only released through auction settlement or refund processing. |
| Atomic Settlement | All payment splits for all slots in an event trigger (broadcaster share + platform fee per slot) execute in a single transaction. Either everything succeeds or everything reverts. No partial states. |
| Event Type | A category of cricket moment that triggers an auction (e.g., OVER_BREAK, WICKET_FALL, LAST_OVER_THRILLER). |
| Platform Fee | The percentage taken by the protocol on every successful auction settlement. Only charged when an auction settles. Not charged on reservation fees. |
| Intra-Event Exclusion | Competing brands in the same exclusion group cannot both win slots within the same ad break (same event trigger). |
| Cross-Event Exclusion | Competing brands in the same exclusion group cannot win slots in consecutive ad breaks (across different event triggers), subject to the configured separation distance. |
